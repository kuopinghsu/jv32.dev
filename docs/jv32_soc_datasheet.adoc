JV32 is a compact 32-bit RISC-V System-on-Chip (SoC) for RTL simulation and FPGA prototyping. It integrates a single-issue 3-stage processor core, instruction and data TCM, AXI4-Lite interfaces, UART, CLIC/CLINT-compatible timer functions, simulation support, and JTAG/cJTAG debug connectivity.

This datasheet describes the implemented RTL behavior. Unless stated otherwise, addresses, reset values, timing, and feature descriptions refer to the default RTL parameters.

== Introduction

=== SoC Overview

The JV32 SoC is a compact embedded processor system. The default configuration implements RV32IMAC with M-mode (M-mode). The main blocks are:

* **Processor core** (`jv32_core`): single-issue 3-stage pipeline (IF → EX → WB), RVC expansion, configurable multiply/divide/shift units, branch prediction, and atomic-operation support
* **Tightly Coupled Memories (TCM)**: 128 KB IRAM at `0x8000_0000` and 128 KB DRAM at `0x9000_0000` by default, with 1-cycle read latency
* **Merged AXI4-Lite Master**: Out-of-TCM accesses from both I-fetch and D-bus share one master port; D-bus has priority over I-fetch
* **AXI4-Lite Slave**: External agents (debug master, testbench DPI) can read/write TCM; core has absolute priority
* **Peripheral Subsystem** (4-slave AXI crossbar): UART, CLIC, Magic device, external catch-all
* **Interrupt System**: CLIC with CLINT-compatible 64-bit timer (`mtime`/`mtimecmp`), software interrupt (`msip`), and 16 independently prioritized external interrupt lines

=== Document Conventions

This datasheet describes the behavior implemented by the supplied RTL. Unless a section explicitly states otherwise:

* Address ranges and reset values refer to the default RTL parameters unless explicitly marked as parameter-dependent.
* `R/O`, `R/W`, and `W/O` mean read-only, read/write, and write-only.
* Multi-byte values use little-endian byte order.
* AXI response names use the AXI4-Lite encodings `OKAY`, `SLVERR`, and `DECERR`.
* Signal names and RTL parameter names are shown in monospace, for example `ext_irq_i` and `IRAM_SIZE`.
* Optional features are identified by the RTL parameter that enables them.
* Software must not rely on undocumented or reserved register bits. Unless explicitly stated otherwise, software should write zero to reserved bits and ignore reserved bits when reading.
* “Implemented” means that an active RTL path provides the stated behavior; a declared constant or unused encoding alone is not treated as an implemented feature.
* `must` identifies a software or integration requirement. `should` identifies a recommended practice. Descriptive statements define RTL behavior.
* Reset values apply to the corresponding RTL state after reset has been asserted. Software-visible state may change immediately after reset is released as counters, timers, or execution begin.

=== Scope and Implementation Notes

The datasheet is an RTL functional specification. It does not define FPGA- or ASIC-specific timing closure, maximum clock frequency, power, area, or electrical characteristics. Those values depend on the target technology, synthesis constraints, and physical implementation.

Unless stated otherwise, sizes, counts, base addresses, and enabled features use the RTL default parameters. If an integration changes a parameter, the corresponding feature, memory size, or ISA capability may also change.

Behavior outside the documented address ranges, register encodings, access sizes, or enabled feature set is not part of the software interface unless the relevant section explicitly defines it.

Microarchitectural details such as pipeline timing, arbitration timing, and internal state transitions describe the current RTL implementation. Software must not depend on cycle-exact behavior unless a section explicitly defines that behavior as part of the interface.

=== System Components

==== Processor and Memory Integration

The processor and integrated memory-mapped interfaces use little-endian byte ordering. Bit numbering follows the RISC-V convention: bit 0 is the least-significant bit. Addresses are byte addresses.

The `jv32_core` processor implements a single-issue 3-stage in-order pipeline:

* **Instruction Fetch (IF)**: PC generation, RVC expansion, instruction fetch request
* **Execute (EX)**: Decode, register read, ALU, address calculation, CSR operations, hazard detection
* **Writeback (WB)**: Memory result, register writeback, branch redirect, exception handling

The core supports:

* Single-issue in-order execution; Slot-A all instructions; no dual-issue
* WB→EX same-cycle forwarding for RAW hazard resolution
* 1-cycle load-use stall (EX→WB stall + IF hold)
* 1-cycle branch/jump flush (EX squashes IF on misprediction or unconditional redirect)
* Multi-cycle stall for slow divide/shift and for multiply when scoreboard dispatch is not active
* Optional single-slot non-blocking scoreboard (`SCOREBOARD_EN`) for multi-cycle `MUL`: independent younger instructions may issue while preserving in-order retirement
* AMO (LR/SC and AMO operations) via a 3-state machine (IDLE → LOAD_WAIT → STORE_WAIT)
* Configurable branch predictor (`BP_EN`, static not-taken fallback when disabled)
* CLIC-aware CSR unit with CLIC interrupt-level threshold (`mintthresh`), current level (`mintstatus`), vectored-trap base (`mtvt`), next-interrupt fast-claim (`mnxti`), and hardware tail-chaining on `mret`

==== TCM: IRAM and DRAM (`jv32_top`)

Both TCM regions are instantiated inside `jv32_top` as a single 32-bit wide `sram_1rw` primitive per region, with byte-enable write support:

* **IRAM**: instance `u_iram`, base `IRAM_BASE` (default `0x8000_0000`), size `IRAM_SIZE` (default 128 KB); 32-bit data word, 4-bit write-byte-enable
* **DRAM**: instance `u_dram`, base `DRAM_BASE` (default `0x9000_0000`), size `DRAM_SIZE` (default 128 KB); same arrangement
* **1-cycle read latency**: Address presented at cycle N returns data at cycle N+1
* **Contention resolution**: When I-fetch and D-access both target IRAM, D-access wins; I-fetch stalls 1 cycle
* **SRAM arbitration priority**: Core-D > Core-I > AXI Slave

==== Merged AXI4-Lite Master

Out-of-TCM accesses from I-fetch and D-bus share one AXI4-Lite master (`m_axi_*`):

* D-bus has priority over I-bus when both miss TCM simultaneously
* Both are served sequentially (not simultaneously)
* I-fetch AXI transaction is cancelled/replaced if a branch redirect arrives during the outstanding fetch

==== AXI4-Lite Slave

External agents (debug master, pre-simulation ELF loader via DPI) access TCM through the slave port (`s_axi_*`):

* Core has absolute priority; slave stalls until the target SRAM is idle for the current cycle
* The slave read-data register latches SRAM output on the first granted cycle and holds it until the bus handshake completes
* For pre-simulation ELF loading, the recommended method is DPI `mem_write_byte` (direct SRAM array access), which is faster than AXI slave transactions

==== Peripheral AXI Crossbar

A 1-to-4 AXI4-Lite crossbar routes out-of-TCM transactions from `jv32_top`'s merged master to three named peripheral slaves (UART, CLIC, Magic) plus a fourth external catch-all slave. Address decode uses base/mask comparison (see <<_memory_map>>).

== Processor Core Specification

=== Data Representation

The core uses 32-bit little-endian data representation. Bit 0 is the least-significant bit, and all addresses are byte addresses. Instruction alignment follows the enabled RISC-V compressed-instruction configuration.

=== ISA Support

=== RV32E Configuration

When `RV32E_EN=1`, the architectural integer register set is reduced to x0–x15. The decoder checks register fields according to the instruction format rather than blindly checking every encoded five-bit field:

* `rs1` is checked only for formats that actually use `rs1`.
* `rs2` is checked for OP, STORE, BRANCH, and AMO formats.
* `rd` is checked only when the decoded instruction writes a GPR.

An instruction that actually references x16–x31 is illegal. Immediate fields that happen to contain bit 4 in the same bit positions are not incorrectly rejected.

The core also forces Zba/Zbb/Zbs inactive and disables the RAS and instruction prefetch buffer when `RV32E_EN=1`. Compressed register-prime encodings use x8–x15 and remain within the RV32E register set.

=== Forwarding and Hazards

[cols="1,1,3"]
.Pipeline Hazard Handling
|===
|Hazard |Type |Description

|RAW (register read-after-write)
|Forwarding
|WB result forwarded to EX operand inputs in the same cycle. No stall required for ALU→ALU dependency.

|Load-use
|Stall (1 cycle)
|Load in EX presents address; data arrives in WB. The following EX-stage instruction must stall 1 cycle waiting for WB to complete. IF is also held.

|Branch / Jump misprediction
|Flush (1 cycle)
|When EX detects a taken branch or unconditional jump, the IF instruction in flight is squashed (1 pipeline bubble).

|Multi-cycle ALU (mul/div/shift)
|Stall / partial overlap
|Without scoreboard dispatch, multi-cycle operations stall EX/IF until completion. |Scoreboard issue gating (`MUL` non-blocking path)
|Issue stall (selective)
|Issue is blocked on RAW (`rs1`/`rs2` busy), WAW (`rd` busy), structural (slot already occupied), or commit-sensitive younger instruction while slot is active. Retirement remains strictly in-order through WB arbitration.

|AMO (LR/SC, AMO operations)

|No-op / Fetch synchronization
|`FENCE` is decoded but treated as a no-op. `FENCE.I` redirects to the sequential PC, flushes the RVC/instruction-prefetch path, discards an in-flight stale AXI instruction response, and suppresses the first stale registered TCM response after the redirect.

NOTE: `FENCE.I` is the instruction-fetch synchronization mechanism implemented by this core. `jv32_top` contains a FENCE.I-specific stale-response suppressor so that an IRAM instruction modified by a preceding TCM store is re-fetched instead of consuming the registered pre-write SRAM response. `FENCE.I` does not add general data-memory ordering semantics; `FENCE` remains a no-op. `sw/fencei_smc` verifies that every store before `FENCE.I` — including sub-word writes and writes issued while the TCM store queue is full — is visible to the subsequent instruction fetch. `sw/mem_ordering` verifies that `FENCE` never needs to add ordering on the current configuration (program order is already preserved across TCM↔TCM and TCM↔MMIO).

NOTE: `WFI` is also decoded but treated as a no-op in `jv32_core`. It does not stall the hart or enter a physical low-power state.

=== Atomic Operation Semantics

When `AMO_EN=1`, the decoder accepts the AMO opcode with `funct3=010` and the core executes LR.W, SC.W, and the implemented AMO.W operations through the atomic state machine.

==== LR/SC Reservation

The RTL uses a single reservation consisting of `lr_valid` and the exact 32-bit address captured when LR.W completes successfully.

* LR.W returns the loaded word and records the LR address.
* SC.W succeeds only when `lr_valid=1` and the SC address exactly matches the saved LR address.
* Successful SC.W returns `0`.
* SC.W without a matching reservation returns `1` and does not issue the store.
* Executing *any* SC.W invalidates the reservation, whether it succeeds or fails. A failing SC.W (address mismatch, or no live reservation) clears `lr_valid` in the same cycle; a matching SC.W clears it when the store transaction completes. This matches the RISC-V A-extension requirement that "regardless of success or failure, executing an SC.W instruction invalidates any reservation held by this hart".
* Ordinary loads, stores, traps, interrupts, and unrelated AMO operations by the hart itself do not clear `lr_valid`. For a single-hart system this is a legal implementation choice; a later SC.W is still bounded because the first SC.W in program order clears the reservation.
* A debug-module memory write — SBA or an abstract Access Memory command — to the reserved word invalidates the reservation on the next cycle, so an SC.W paired with an LR.W that the debugger overwrote fails. The comparison is word-granular and on canonical (de-aliased) addresses.

`aq` / `rl` bits on atomics are decoded but do not change core behaviour: the in-order single-issue pipeline and store queue already retire memory and I/O operations in an order at least as strong as every acquire/release case on this single-hart configuration (verified by `sw/mem_ordering`).

==== AMO Encoding Scope

The supported AMO.W operations are `AMOSWAP`, `AMOADD`, `AMOXOR`, `AMOAND`, `AMOOR`, `AMOMIN`, `AMOMAX`, `AMOMINU`, and `AMOMAXU`, plus LR.W and SC.W.

The decoder validates `AMO_EN`, requires `funct3=010`, and WARL-checks `funct5`: only the eleven architecturally defined encodings above are accepted. Every other `funct5` value under the AMO opcode raises an illegal-instruction exception and issues no memory transaction.

==== Atomic Alignment

All implemented atomic operations are word operations and require a naturally aligned 32-bit address. A misaligned LR.W / SC.W / AMO.W address is detected in the EX stage and raises an address-misaligned exception before any memory transaction is issued: cause 4 (load address misaligned) for LR.W, and cause 6 (store/AMO address misaligned) for SC.W and every AMO.W. `mtval` holds the faulting address.

=== Control-Flow Prediction

When `BP_EN=1` (default), the front end combines static BTFNT conditional-branch prediction, one-entry last-branch reuse, JAL predecode, and the optional Return Address Stack (RAS). `BP_EN=0` disables these speculative front-end redirects.

==== Conditional Branch Prediction

For a conditional branch, the front end applies the following prediction rules:

. A valid one-entry last-branch (`L0`) hit for the same branch PC reuses the most recently resolved taken target.
. Otherwise, a backward branch (negative B-immediate) is predicted taken.
. A forward branch is predicted not taken.
. EX resolves the actual branch condition. A mismatch between the prediction and the resolved result redirects the fetch PC and flushes the speculative path.

The L0 entry is updated whenever a branch resolves and records that branch PC, resolved target, and whether the branch was taken. This allows a recently observed forward-taken branch to be predicted taken even though the normal BTFNT rule predicts forward branches as not taken.

When `BP_EN=0`, conditional branches are predicted not taken and a taken branch redirects from EX.

==== JAL

The front end recognizes JAL after RVC expansion and computes its PC-relative target before the instruction reaches EX. When front-end prediction is active, the fetch path redirects directly to that target. EX still computes the architectural JAL target and link value.

The architectural link address is `PC + 2` for a compressed call expanded by the RVC front end and `PC + 4` for a 32-bit JAL/JALR instruction.

==== JALR

JALR computes the architectural target in EX as:

----
target = (rs1 + immediate) & ~1
----

Bit 0 of the target is therefore always cleared.

A general JALR is not target-predicted by BTFNT. Eligible return patterns can instead be predicted by the RAS. If a RAS prediction is absent or does not match the EX-computed target, EX redirects to the computed JALR target.

==== Return Address Stack

The RAS is active only when `BP_EN=1`, `RAS_EN=1`, and `RV32E_EN=0`. It is a two-entry circular structure.

* **Push**: JAL or JALR with `rd` equal to `x1` (`ra`) or `x5` (`t0`) pushes the sequential return address.
* **Pop**: JALR with `rs1` equal to `x1` or `x5` and `rd` not equal to either link register uses and removes the current RAS top when the stack is non-empty.
* **Push + pop**: a JALR pattern that both reads and writes a link register is treated as a coroutine-style operation; the current top entry is replaced while the RAS pointer is unchanged.
* **Empty RAS**: no speculative return redirect is made.
* **Non-speculative redirect**: exception, MRET, or interrupt redirect clears the RAS state.
* **Branch correction and FENCE.I**: these redirects do not clear the RAS.

A RAS prediction is only speculative. EX always computes the JALR target and corrects the fetch path if the predicted return address is wrong.

==== Exception Detection Priority

For an instruction reaching EX, the core checks synchronous conditions in this order:

. instruction-fetch access fault;
. illegal instruction (includes reserved AMO `funct5` encodings);
. EBREAK that is not redirected into Debug Mode;
. ECALL;
. load/store/AMO address misalignment (normal loads and stores, and LR.W / SC.W / AMO.W).

The first matching condition is recorded in the EX/WB pipeline state. Data-memory AXI faults are detected later in WB and become load/store access-fault exceptions. Because illegal-instruction ranks above the misalignment check, a reserved AMO encoding with a misaligned address reports illegal instruction.

==== Redirect and Trap Priority

At the WB redirect point, the current RTL applies the following priority:

. synchronous exception or data-memory access fault;
. MRET;
. pending interrupt;
. EX-stage control-flow redirect such as a branch correction, JALR correction, or FENCE.I.

A pending interrupt therefore does not override an older synchronous exception or an MRET already in WB. When an interrupt is accepted, the WB instruction is canceled rather than retired; its PC is saved as the interrupt `mepc` so that it is re-executed after MRET.

During single-step execution, normal interrupt acceptance is suppressed while the step is pending. CLIC MRET tail chaining is handled separately: if MRET executes while a CLIC interrupt above `mintthresh` is pending, the core redirects directly to the next CLIC vector instead of first returning to `mepc`.

==== Trap Handling Sequence

On exception or interrupt:

1. `mstatus.MPIE ← mstatus.MIE`; `mstatus.MIE ← 0` (disable interrupts)
2. `mstatus.MPP ← 2'b11` (M-mode)
3. `mepc ← PC of interrupted/excepted instruction`
4. `mcause ← {1'b1/1'b0, cause_code}`
5. `mtval ← faulting_address` (or 0)
6. PC redirected to `mtvec` (direct mode) or `mtvec + 4*cause` (vectored mode)

CLIC vectored interrupts redirect to `mtvt + 4*clic_id` (vector table indexed by the winning interrupt's ID) and set `mintstatus.mil` to the claimed interrupt level.

Normal MRET restores: `mstatus.MIE ← mstatus.MPIE`; `mstatus.MPIE ← 1`; PC ← `mepc`.

==== Tail-Chaining (Hardware)

If, at the moment `mret` retires, a CLIC external interrupt is pending with level > `mintthresh`, the core performs a **tail-chain** rather than a full context restore:

* Fetch is redirected to `mtvt + 4*clic_id` (the next handler) — zero overhead cycles.
* `mstatus.MIE` remains 0 (already in a new handler).
* `mstatus.MPIE` is set to 1 (so the eventual chain-terminating `mret` re-enables MIE).
* `mepc` is unchanged (still holds the preempted task's return address).
* `mcause` is updated to `0x8000_000B` (machine external interrupt).
* `mintstatus.mil` is updated to the new interrupt's level.

Tail-chaining eliminates the push/pop overhead between consecutive ISRs of equal or lower priority and is fully transparent to software: the same trap handler is re-entered for each chained interrupt.

==== Software-Assisted Tail-Chain (`mnxti`)

Within a CLIC handler, software can voluntarily tail-chain to the next pending interrupt by reading `mnxti`:

[source,c]
----
uintptr_t next_pc = csr_swap(mnxti, 0);
if (next_pc) goto (void *)next_pc;   // chain to next handler
----

When `mnxti` is written (any write, e.g. `csrrsi mnxti, 0`) and a qualifying interrupt is pending:

* `mcause` and `mintstatus.mil` are atomically updated to the new interrupt.
* `mstatus.MIE` is re-enabled (nested interrupt within the handler).
* The read value is `mtvt + 4*clic_id` of the newly claimed interrupt (or 0 if none).

Software branches to the returned address to begin serving the next interrupt without an `mret`/re-entry cycle.

=== TCM AXI Slave Semantics

The TCM slave path uses `axi_ram_ctrl` and the shared single-port SRAM.

* AW and W may arrive independently; each channel is held until both parts of the write transaction are available.
* `WSTRB[3:0]` directly controls the four SRAM byte write enables.
* The address presented to SRAM is `addr >> 2`; low address bits `[1:0]` are not checked. Software and external masters must therefore issue naturally aligned accesses.
* A read returns AXI `OKAY`; no address-alignment error is generated by `axi_ram_ctrl`.
* If a RAM controller instance is configured with `WR_EN=0`, writes return `SLVERR`; writable TCM instances return `OKAY`.
* SRAM contents are not initialized by `sram_1rw` reset. Program/data initialization is supplied by the simulation/FPGA integration flow.

NOTE: `axi_clic` always returns AXI `OKAY` for reads and writes. Unsupported offsets read as zero and writes have no effect. Software therefore must not use the AXI response code to discover whether a CLIC offset is implemented.

==== Timer Operation

The 64-bit `mtime` counter increments by 1 every system clock cycle. The timer interrupt fires when `mtime >= mtimecmp` (unsigned 64-bit comparison), **unless `mtimecmp` equals its reset sentinel value `0xFFFF_FFFF_FFFF_FFFF`** (startup guard — prevents a spurious interrupt before software programs a compare value). Software clears the timer interrupt by writing a new, larger value to `mtimecmp`.

[source,c]
----
// Set timer 1 ms from now (100 MHz clock)
uint64_t now = ((uint64_t)CLIC_MTIME_HI << 32) | CLIC_MTIME_LO;
uint64_t cmp = now + 100000;   // 1 ms at 100 MHz
CLIC_MTIMECMP_LO = (uint32_t)(cmp & 0xFFFFFFFF);
CLIC_MTIMECMP_HI = (uint32_t)(cmp >> 32);
----

WARNING: Always write MTIMECMP_HI (set to `0xFFFFFFFF`) before writing
MTIMECMP_LO when programming a new compare value, to avoid a spurious timer
interrupt in the window between the two writes on a 64-bit counter.

==== Software Interrupt Operation

Write `MSIP[0] = 1` to assert machine software interrupt immediately, `0` to clear.

==== External Interrupt Operation

Each `ext_irq_i[n]` input is gateable via `CLICINT[n].ie`. When any enabled and pending external interrupt has `ctl` (priority level) greater than the current `mintthresh` CSR value, `clic_irq_o` is asserted to the core as an M-mode external interrupt.

When a CLIC interrupt is eligible (`clic_irq` asserted above `mintthresh`) and global machine interrupts are enabled, the CSR interrupt selector gives the CLIC path precedence over the conventional MEI/MTI/MSI inputs. The CLIC asserts `clic_id_o[4:0]` with the index of the winning pending enabled interrupt. Arbitration scans interrupt IDs in ascending order and replaces the current winner only when a strictly greater `clicint_ctl` value is found. Therefore, when two pending interrupts have the same `ctl` value, the lower interrupt ID wins. Both `clic_level_o[7:0]` and `clic_prio_o[7:0]` carry the same `clicint_ctl[winner]` value; this RTL does not implement separate level and priority fields. The CPU uses this to compute the handler address as `mtvt + 4*clic_id` (where `mtvt` is programmed to a 4-byte-pointer table). This happens automatically on interrupt entry and on hardware tail-chain at `mret`; software can also perform the same lookup by reading `mnxti`.

[NOTE]
**UART IRQ routing**: the UART `irq` output (asserted when `(IE & IS) != 0`) is OR'd into `ext_irq_i[0]` inside `jv32_soc` before being presented to the CLIC. The effective `CLICINT[0].ip` thus reflects `ext_irq_i[0] | uart_irq`. Software must enable `CLICINT[0].ie` and configure `CLICINT[0].ctl` to receive UART interrupts. The external `ext_irq_i[0]` SoC pin is still available and is ORed with the UART interrupt.

=== Crossbar Architecture

The `axi_xbar` module implements a 1-to-N address-decoder crossbar:

* **Address decode**: `(addr & SLAVE_MASK[i]) == (SLAVE_BASE[i] & SLAVE_MASK[i])` for each slave in order; first match wins
* **Decode ordering**: slave indices are checked in ascending order and the first matching base/mask entry wins.
* **Crossbar-local decode error**: if no configured slave entry matches, the crossbar returns `DECERR` on both reads and writes.
* **SoC catch-all target**: the fourth `jv32_soc` decode entry uses base `0x0000_0000` and mask `0x0000_0000`, so every address not claimed by UART, CLIC, or Magic matches the external AXI target. In the default SoC integration, crossbar-local `DECERR` is therefore normally unreachable; the external target supplies the final response.
* **Protocol scope**: the exposed interconnect is AXI4-Lite and carries only single-beat transactions; there are no burst-length, burst-type, ID, or `RLAST` ports.

== Debug and JTAG

=== Debug Architecture

When `JTAG_EN=1`, the SoC instantiates the JTAG TAP, RISC-V Debug Transport Module (DTM), Debug Module control logic, abstract-command engine, System Bus Access (SBA), and hardware trigger support.

The Debug Module conforms to **RISC-V Debug Specification 1.0**: `dmstatus.version` reads 3 and `dtmcs.version` reads 1 (the DTM encoding shared by spec 0.13 and 1.0). Optional 1.0 features that JV32 does not implement read back as "absent": `dmstatus.hasresethaltreq` = 0 (no halt-on-reset), `dmstatus.confstrptrvalid` = 0 (no configuration string), `dtmcs.errinfo` = 0, and the `dmcs2`/`hawindow`/`confstrptr0-3` registers return 0. `dmstatus.ndmresetpending` tracks `dmcontrol.ndmreset`; `dmstatus.stickyunavail` = 0 (the single hart is always present). `nextdm` (DMI 0x1d) reads 0 — this is the only Debug Module.

The implementation spans two clock domains:

* The TAP and DMI register bank operate in the TAP clock domain.
* Debug command execution, register access, memory access, and core control operate in the system-clock domain.
* Clock-domain crossings use synchronizers, toggle handshakes, or stable-payload transfer mechanisms implemented in `jtag_tap.sv` and `jv32_dtm.sv`.

When `JTAG_EN=0`, the debug logic is not instantiated and the associated debug outputs are tied to inactive values.

=== Abstract Commands

The Debug Module implements Access Register and Access Memory command types.

==== Access Register

Supported register transfers use a 32-bit abstract access size.

The implemented register-number handling includes:

* Integer registers `x0`–`x31` through abstract register numbers `0x1000`–`0x101F`.
* `dpc` at CSR number `0x7B1`.
* Debug and machine CSRs below `0x1000` through the debug CSR path.
* `transfer=0, postexec=0` as a valid no-operation command.
* `postexec` execution through the two-word program buffer.

Commands requiring an unsupported access size report an abstract-command not-supported error (`cmderr=2`). Commands that require hart access while the hart is running report a halt/resume error (`cmderr=4`). An abstract access to a CSR the core does not implement fails with `cmderr=3` (exception) and performs no write — so a debugger probing for optional CSRs (e.g. vector `vlenb`, the AIA `mtopi`/`miselect` registers) is told the CSR is absent rather than receiving a spurious zero.

==== Access Memory

Access Memory supports 8-, 16-, and 32-bit transfers. `aamvirtual` is not implemented. Access sizes larger than 32 bits are reported as unsupported.

DATA1 supplies the address. DATA0 supplies or receives the transfer data. Address post-increment is supported by the RTL command engine.

=== System Bus Access (SBA)

SBA provides direct debug memory access independently of abstract Access Memory commands.

The RTL implements:

* 8-bit, 16-bit, and 32-bit accesses.
* `sbreadonaddr`.
* `sbreadondata`.
* `sbautoincrement`.
* `sbbusy` and `sbbusyerror`.
* SBA error reporting and write-one-to-clear error handling.

`sbbusyerror` is set whenever the debugger writes `SBADDRESS0` or `SBDATA0`, or
reads `SBDATA0`, while a system bus access is in progress (`sbbusy=1`); the
interfering `SBADDRESS0`/`SBDATA0` write is discarded (the shadow register keeps
its value). No SBA access is started while `sberror` or `sbbusyerror` is set;
both are cleared write-one-to-clear via `SBCS`.

The debug-bus response timeout (used by SBA and by abstract Access Memory) is a
counter of parameterized width `DBG_BUS_TIMEOUT_W` (default 12 → 4095 cycles,
about 41 µs at 100 MHz). A response later than the timeout reports `sberror=1`
(SBA) or `abstractcs.cmderr=5` (abstract memory). Integrators with very slow
debug targets can widen the parameter.

=== Hardware Triggers

Trigger matching occurs in EX with timing-before behavior: a matching instruction is halted before it is promoted for normal execution. A trigger is eligible only when its type is 2, M-mode enable bit is set, and `action=1` requests Debug Mode entry.

The RTL supports:

* execute match against the instruction PC;
* load match against the effective data address;
* store match against the effective data address;
* exact address match (`match=0`);
* NAPOT address match (`match=1`) for load/store triggers.

Execute matching is exact-PC only in the current core. Unsupported `match` values fall back to exact comparison in the RTL helper.

If EBREAK debug-entry and a hardware trigger coincide, the debug-halt bookkeeping records the trigger as the halt cause (`trigger_halt`) and does not mark EBREAK as the separate halt cause. Multiple trigger slots may report hit simultaneously.

The default RTL implements two trigger slots (`N_TRIGGERS=2`). `N_TRIGGERS` is fully parameterized in both the core and the debug module: the trigger register bank, its reset values, the per-trigger hit-latch, and the `tselect` index are all generated from `N_TRIGGERS`, and the design elaborates for `N_TRIGGERS` = 1, 2, or 4. `tselect` is WARL to `[0, N_TRIGGERS)`.

=== cJTAG Bridge

When `USE_CJTAG=1`, `cjtag_bridge.sv` converts the external two-wire TCKC/TMSC interface to the internal JTAG TAP signals.

The bridge implements:

* Two-stage synchronization of TCKC and TMSC into the system-clock domain.
* TCKC edge detection.
* TMSC escape-sequence detection.
* OScan1 serialized scan transport.
* TAP.7 star-2 activation behavior implemented by the state machine.
* Registered generation of the internal TAP clock and JTAG data/control signals.

The RTL requires each TCKC high and low phase to remain stable long enough to pass through the two-stage synchronizer and edge detector. The source comments specify the design requirement `f_sys >= 6 × f_tckc`. This is a functional sampling requirement, not an FPGA/ASIC timing-closure guarantee.

==== TAP Clock — `USE_CJTAG=0` (4-wire JTAG)

In 4-wire JTAG mode, `jtag_pin0_tck_i` directly clocks the TAP. TCK is asynchronous to the system clock. Status and command information crossing between the TAP and system-clock domains is synchronized in the debug logic.

The RTL does not define a universal maximum external TCK frequency. The usable TCK frequency depends on the implementation timing and on the clock-domain-crossing handshake latency. The DTMCS `idle=1` field requires the debugger to insert at least one Run-Test/Idle TCK cycle between DMI operations.
==== TAP Clock — `USE_CJTAG=1` (2-wire cJTAG)

In 2-wire cJTAG mode, `jtag_pin0_tck_i` carries TCKC and `jtag_pin1_tms_i/o` carries TMSC. `cjtag_bridge` samples both external signals using the system clock, detects synchronized TCKC edges, and generates the internal TAP clock and JTAG scan signals.

The bridge source defines the functional sampling requirement:

----
f_sys >= 6 × f_tckc
----

This corresponds to at least three system-clock cycles for each TCKC high or low phase, allowing the two-stage synchronizer and edge detector to observe the signal reliably at the RTL interface level.

The ratio above is a functional design requirement. Actual board-level and FPGA/ASIC timing margins must be established by the target implementation.
==== Reset Architecture

The SoC implements an **asynchronous-assert / synchronous-deassert** reset
pattern.  Two independent sources can assert reset: the external `rst_n` pin
and the debug non-debug-module reset (`dbg_ndmreset`) asserted by the RISC-V
Debug Module via JTAG.

===== Reset signal flow

[source,systemverilog]
----
// jv32_soc.sv
assign rst_n_pre = rst_n & ~dbg_ndmreset;   // (1) OR of both reset sources

always_ff @(posedge clk or negedge rst_n_pre) begin
    if (!rst_n_pre) begin
        rst_sync_ff1 <= 1'b0;               // (2) async assert: both FFs cleared immediately
        rst_sync_ff2 <= 1'b0;
    end else begin
        rst_sync_ff1 <= 1'b1;               // (3) synchronous deassert: propagates over 2 clk cycles
        rst_sync_ff2 <= rst_sync_ff1;
    end
end

assign soc_rst_n = rst_sync_ff2;            // (4) clean synchronised reset to all SoC logic
----

===== Reset domain coverage

`soc_rst_n` (the synchronised output of the 2-FF chain) is distributed to:

* `jv32_top` — processor pipeline, TCM SRAM control registers, AXI master/slave
* `axi_clic` — CLIC/CLINT registers (`mtime`, `mtimecmp`, `msip`, interrupt pending)
* `axi_uart` — UART TX/RX FIFOs and baud rate generator
* `axi_xbar` — AXI crossbar state

The JTAG TAP (`jtag_tap`) and `jv32_dtm` are reset by `rst_n` **directly** (not
through the synchroniser), so debug infrastructure is available as soon as the
external reset is released, independent of the 2-cycle delay on `soc_rst_n`.
`jtag_ntrst_i` provides an additional TAP-only reset.

== Programming Guide

=== MMIO Access Rules

Peripheral registers are 32-bit memory-mapped registers unless a register description states otherwise. Software should use naturally aligned 32-bit accesses for control and status registers. Reserved offsets must not be used as part of the programming interface.

For device programming sequences, software should complete required configuration writes before enabling the corresponding interrupt or operation. The current RTL treats `FENCE` as a no-op, so software must not rely on it to create an additional hardware data-memory barrier. `FENCE.I` is implemented separately and flushes/refetches the instruction path for instruction-memory synchronization.

=== Access and Error Handling

Software must treat an AXI error response as a failed access. Error behavior is target-specific: UART and Magic can return `SLVERR` for unsupported addresses, while CLIC returns `OKAY` and zero/no-effect behavior for unsupported offsets. Addresses routed to the external AXI interface may return any response permitted by the connected target or interconnect.

Software and external masters should use naturally aligned accesses. Several RTL blocks select registers or SRAM words using upper address bits and do not independently reject all misaligned accesses.

=== Boot Sequence

The processor boots from `BOOT_ADDR` (default `0x8000_0000` = IRAM base). The reset vector is hardwired to `BOOT_ADDR & ~3` (word-aligned).

For simulation, the typical boot flow is:

1. ELF loaded into TCM via DPI (`mem_write_byte`) before simulation starts
2. Simulation starts, core fetches from `BOOT_ADDR` (mapped to IRAM, 1-cycle latency)
3. Startup code (`startup.S`) initialises stack pointer to top of DRAM
4. Hardware CSRs initialized: `mstatus`, `mtvec`, `mie`
5. Peripherals initialized (UART starts with the parameter-derived baud divisor; software may change it at runtime; CLIC `mtimecmp` is programmed as required)
6. `mstatus.MIE` set to enable interrupts
7. Jump to `main()`

=== Stack Configuration

Default linker script maps DRAM to data/BSS/stack:

----
Stack top: DRAM_BASE + DRAM_SIZE - 4    (e.g. 0x9001_FFFC)
Stack grows downward into DRAM
Data/BSS:  DRAM_BASE (loaded by startup.S from IRAM)
----

=== Interrupt Handling

==== Setting Up Interrupts

[source,c]
----
#include "csr.h"

extern void trap_entry(void);  // defined in startup.S

void setup_interrupts(void) {
    // Set trap vector (direct mode: mtvec points to handler)
    write_csr(mtvec, (uint32_t)trap_entry);

    // Enable M-mode interrupts in mstatus
    set_csr(mstatus, 0x8);  // MIE bit

    // Enable timer + external + software interrupts in mie
    set_csr(mie, (1<<7) | (1<<11) | (1<<3));  // MTIE | MEIE | MSIE

    // Program CLIC mtimecmp for periodic 1ms timer (100 MHz)
    volatile uint32_t *mtime_lo    = (uint32_t *)0x02004000;
    volatile uint32_t *mtime_hi    = (uint32_t *)0x02004004;
    volatile uint32_t *mtimecmp_lo = (uint32_t *)0x02004008;
    volatile uint32_t *mtimecmp_hi = (uint32_t *)0x0200400C;

    // Set mtimecmp_hi first to avoid spurious IRQ
    *mtimecmp_hi = 0xFFFFFFFF;
    uint64_t now = ((uint64_t)*mtime_hi << 32) | *mtime_lo;
    uint64_t cmp = now + 100000;  // 1 ms @ 100 MHz
    *mtimecmp_lo = (uint32_t)cmp;
    *mtimecmp_hi = (uint32_t)(cmp >> 32);
}
----

==== Trap Handler

[source,c]
----
void trap_handler(uint32_t mcause_val) {
    if (mcause_val & 0x80000000) {
        // Interrupt
        uint32_t cause = mcause_val & 0x7FFFFFFF;
        switch (cause) {
        case 7:   // Machine timer interrupt
            handle_timer_irq();
            break;
        case 11:  // Machine external interrupt (CLIC)
            handle_clic_irq();
            break;
        case 3:   // Machine software interrupt
            handle_sw_irq();
            break;
        }
    } else {
        // Synchronous exception
        handle_exception(mcause_val);
    }
}

void handle_timer_irq(void) {
    // Clear by advancing mtimecmp
    volatile uint32_t *cmp_lo = (uint32_t *)0x02004008;
    volatile uint32_t *cmp_hi = (uint32_t *)0x0200400C;
    uint64_t cmp = ((uint64_t)*cmp_hi << 32) | *cmp_lo;
    cmp += 100000;  // next 1 ms
    *cmp_hi = 0xFFFFFFFF;  // prevent spurious IRQ during update
    *cmp_lo = (uint32_t)cmp;
    *cmp_hi = (uint32_t)(cmp >> 32);
}

void handle_clic_irq(void) {
    // CLIC vectored entry: mcause = 0x8000_000B, mintstatus.mil = this IRQ's level.
    // Scan CLICINT[n].ip to identify the source; IP auto-clears when ext_irq_i[n] deasserts.
    for (int n = 0; n < 16; n++) {
        volatile uint32_t *clicint = (uint32_t *)(0x02001000 + n * 4);
        if (*clicint & 0x1) {
            // Source n is pending — handle it here.
        }
    }
    // Software-assisted tail-chain: check for next pending IRQ via mnxti.
    // If a higher-priority IRQ arrived during this handler, chain directly to it.
    uintptr_t next = read_csr(mnxti);
    if (next) {
        // Claim it (sets mcause, mintstatus.mil, re-enables MIE) and branch.
        write_csr(mnxti, 0);
        ((void (*)(void))next)();
    }
    // Hardware tail-chain: if another CLIC IRQ above mintthresh is pending
    // when this handler's mret executes, the CPU redirects to mtvt+4*id
    // automatically — no code change needed.
}
----

=== UART Usage

[source,c]
----
#define UART_DATA   (*(volatile uint32_t *)0x20010000)
#define UART_STATUS (*(volatile uint32_t *)0x20010004)
#define UART_IE     (*(volatile uint32_t *)0x20010008)
#define UART_IS     (*(volatile uint32_t *)0x2001000C)

// Poll-mode transmit
void uart_putc(char c) {
    while (UART_STATUS & 0x1);  // wait until TX not full
    UART_DATA = c;
}

// Poll-mode receive
char uart_getc(void) {
    while (!(UART_STATUS & 0x4));  // wait until RX not empty
    return (char)(UART_DATA & 0xFF);
}

// Print string
void uart_puts(const char *s) {
    while (*s) uart_putc(*s++);
}
----

=== Performance-Oriented Programming Considerations

The following items are implementation-aware guidance, not architectural requirements:

* Place latency-sensitive code and data in TCM when deterministic local-memory access is desired.
* Schedule independent instructions between a load and its first consumer when practical to avoid a load-use stall.
* Select `FAST_MUL`, `FAST_DIV`, and `FAST_SHIFT` according to the required area/latency trade-off.
* Avoid unnecessary D-side accesses to IRAM when instruction-fetch contention matters.
* Measure complete workloads on the target configuration; this datasheet does not define a typical CPI or system performance target.

=== Heartbeat Output

`heartbeat_o` is a single-bit observability output derived from bit 24 of the `minstret` counter in `jv32_csr`. It changes state as instructions retire and can be connected to an LED, logic analyzer, or testbench monitor.

[cols="1,1,1,3"]
.Heartbeat Pin
|===
|Signal |I/O |Width |Description

|`heartbeat_o`
|Output
|1
|`minstret[24]`. The output toggles every `2^24` retired instructions. One complete low-to-high-to-low period spans `2 × 2^24` retired instructions.
|===

The period depends on the average cycles per retired instruction (CPI):

----
T = (2 × 2^24 × CPI_avg) / f_clk
----

For example, at the default 100 MHz system clock and `CPI_avg = 1.0`, one complete period is approximately 336 ms. Real software may have a longer period because stalls, memory accesses, branches, and multi-cycle operations increase CPI.

== Release and Integration Checklist

Before releasing an RTL configuration or software package, verify:

* ISA feature parameters and the resulting programmer-visible instruction set.
* `misa` against the enabled MISA-visible extensions.
* IRAM/DRAM sizes, linker-script regions, and canonical/alias address use.
* UART clock assumptions and the reset/default baud divisor.
* CLIC interrupt count, vector base, `mintthresh`, and enabled interrupt controls.
* External AXI address ownership and expected responses for non-internal addresses.
* JTAG/cJTAG mode selection, TAP connectivity, debug reset behavior, and supported DMI flow.
* SRAM/TCM initialization mechanism for the selected simulation, FPGA, or ASIC environment.
* Software headers and register definitions against the detailed block sections in this datasheet.
* Verification results for ISA compliance, AXI protocol compliance, target timing closure, and any target-specific electrical requirements.

Any parameter change that affects software-visible behavior should update the RTL, this datasheet, software headers, linker configuration, and verification environment together.
